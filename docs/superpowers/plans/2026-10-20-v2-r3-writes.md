# jira-delivery-mcp v2 R3 (Safe Writes) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `jira_add_comment` and `jira_update_issue` (transition, assign to me, remote link), registered only when `JIRA_ENABLE_WRITES=true`, every write behind preview → confirm (token or elicitation), audited, never retried.

**Architecture:** A write layer in `src/writes/` (token store, audit log, guard helpers) plus write methods on `JiraClient` that always send with retries disabled. Two tool modules under `src/server/tools/` use one shared `runGuardedWrite` flow: allowlist → plan → (elicit | token) → apply steps → audit. `markdownToAdf` sits next to `adfToMarkdown`.

**Tech Stack:** TypeScript ESM, `@modelcontextprotocol/server` 2.x, Zod 4, Vitest, Node `crypto` and `fs`.

**Spec:** `docs/superpowers/specs/2026-10-20-v2-r3-writes-design.md` (parent: `2026-10-19-v2-delivery-mcp-design.md` §5)

## Global Constraints

- All R1/R2 Global Constraints still hold.
- Write tools are registered only when `config.enableWrites` is true (`JIRA_ENABLE_WRITES`, trimmed, case-insensitive `true`). Default tool count stays 10.
- Every Jira write request uses `retryPolicy: { maxRetries: 0 }`.
- No Jira write happens on a call that has neither a valid `confirmToken` nor an accepted elicitation with `confirm: true`.
- Tokens: 128-bit random hex, 5-minute TTL, single use, bound to tool + issueKey + SHA-256 of canonical JSON args (sorted keys, `confirmToken` excluded).
- Audit line fields exactly `{ ts, tool, issueKey, action, outcome, detail? }`; never a comment body, token or credential. Path `config.auditLogPath` (`JIRA_DELIVERY_AUDIT_LOG`, default `~/.jira-delivery-mcp/audit.log`), dir mode 0700, file mode 0600.
- Annotations for both tools: `{ readOnlyHint: false, destructiveHint: false, idempotentHint: false, openWorldHint: true }`.
- Tests never contact a real Jira (fixtures only).

## Review Focus

1. **Token replay or tampering** (reuse, a different issueKey, a changed markdown, expiry): refused, and no write request is sent. Pinned in Task 3 and Task 4.
2. **A 5xx on a write:** exactly one request is sent and the error is reported, so no duplicate comment. Pinned in Task 1.
3. **Elicitation declined, timed out or unsupported:** falls back to preview + token and never writes. Pinned in Task 4.
4. **Transition name that doesn't exist or matches ambiguously:** lists the available names and writes nothing. Pinned in Task 5.
5. **Audit log not writable** (bad path): the write still happens and a warning is returned, with no crash. Pinned in Task 3.

### Task 3: Write guard core (tokens, audit, allowlist)

**Files:** Create `src/writes/confirmTokens.ts`, `src/writes/auditLog.ts`, `src/writes/guard.ts`. Modify `src/config.ts` (`enableWrites: boolean`, `auditLogPath: string`), `tests/helpers/jiraFixtures.ts` (`fixtureConfig` defaults `enableWrites: false`, `auditLogPath` under the OS tmpdir). Test: `tests/writes/guardCore.test.ts`.

**Interfaces:**
- `class ConfirmTokenStore { issue(tool: string, issueKey: string, args: Record<string, unknown>): string; consume(token: string, tool: string, issueKey: string, args: Record<string, unknown>): boolean }`. It is clock-based on `Date.now()`, so tests use fake timers. `consume` marks the token used before returning true.
- `argsHash(args): string`: canonical JSON with sorted keys, excluding `confirmToken`, then SHA-256 hex.
- `appendAudit(path: string, entry: { tool; issueKey; action: 'comment'|'assign'|'transition'|'link'; outcome: 'applied'|'failed'|'refused'; detail?: string }): string | null`. It adds `ts` (ISO). It returns `null` on success or a warning string on failure, and never throws.
- `assertWritableIssue(issueKey, config): void`: validates the key, and throws `McpInputError` when the strict allowlist is on and the project isn't allowed.

### Task 4: `jira_add_comment` and the shared guarded-write flow

**Files:** Create `src/writes/guardedWrite.ts`, `src/server/tools/jiraAddComment.ts`. Modify `src/server/createServer.ts` (a `ConfirmTokenStore` per server; write registrars only when `config.enableWrites`), `src/server/types.ts` (`ServerDeps.confirmTokens?`). Test: `tests/server/jiraAddComment.test.ts`.

**Interfaces:**
- `WritePlan = { tool: string; issueKey: string; args: Record<string, unknown>; preview: string; steps: Array<{ action: AuditAction; describe: string; run: () => Promise<string /* detail */> }> }`.
- `runGuardedWrite(plan, ctx: { confirmToken?: string; tokens: ConfirmTokenStore; auditLogPath: string; elicit?: ElicitFn }): Promise<{ applied: boolean; preview: string; confirmToken?: string; results: Array<{ action; outcome: 'applied'|'failed'|'skipped'; detail?: string }>; warnings: string[] }>`. Order:
  1. If `confirmToken` is present and consumes → apply.
  2. If present but invalid → refused (audit `refused`), returning the error text from spec §5.2.
  3. Otherwise, if `elicit` is available → ask with the boolean field `confirm`; accept + true → apply.
  4. Otherwise → issue a token and return the preview.
  
  Applying runs the steps in order, stops at the first failure, and audits every attempted step.
- **`jira_add_comment` tool:** input `{ issueKey, markdown: z.string().min(1).max(32000), confirmToken?: z.string() }`. `data` = `{ applied, preview, confirmToken?, results }`. The text is the preview plus "Call again with confirmToken …", or the applied summary. It calls `assertWritableIssue` first. An invalid token → `isError: true`.

- [ ] **Step 1: Failing tests** (fixture `writes`, `connect` with `enableWrites: true` config, and an audit path in a temp dir):
  - listed only when enabled, with the exact annotations
  - first call: no POST sent, and `data.confirmToken` is present
  - second call with the token sends the POST once, and the body equals `markdownToAdf(markdown)`
  - reusing the token → `isError` and no POST
  - same token with changed markdown → `isError` and no POST
  - elicitation accept (`{confirm:true}`) writes in one call
  - decline / `{confirm:false}` / no capability → preview + token, no POST
  - the audit file has one `comment`/`applied` line without the markdown text or the token
  - outside project under strict allowlist → `isError` before any request
- [ ] **Step 2: Run.** Expected: FAIL. **Step 3: Implement.** **Step 4: Run** `npx vitest run tests/server` plus typecheck. **Step 5: Commit**: `feat(server): jira_add_comment behind preview/confirm, elicitation and audit`

### Task 5: `jira_update_issue`

**Files:** Create `src/server/tools/jiraUpdateIssue.ts`. Modify `src/server/createServer.ts`. Test: `tests/server/jiraUpdateIssue.test.ts`.

**Interfaces:**
- Input: `{ issueKey, transitionTo?: z.string().min(1), assignToMe?: z.literal(true), link?: z.object({ url: z.string().url(), title: z.string().min(1).max(255) }), confirmToken?: z.string() }`. It needs at least one action; with none → `isError` "Nothing to update: pass transitionTo, assignToMe or link."
- `link.url` must be http(s); anything else → `isError`.
- Planning reads the transitions (when `transitionTo` is set):
  - Match order: an exact case-insensitive transition `name`; else an exact case-insensitive `to.name`. More than one match on `to.name` → ambiguous.
  - No match or ambiguous → `isError` "No transition matches "<x>". Available: Start Progress (→ In Progress), Ready for QA (→ QA)". Nothing is issued.
- Steps, in order: assign (`getMyself` then `assignIssue`; detail = displayName), transition (detail = target status name), link (detail = url).
- `data` has the same shape as Task 4.
